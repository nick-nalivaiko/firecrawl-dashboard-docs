Practical guide

How the platform works and where each function belongs.

Firecrawl turns web pages and documents into data that software and AI can use. Control Plane adds projects, keys, policies, operations, and observability around a separately versioned Firecrawl Core.

Open dashboardStart with the plain-language guide
The selection rule

One known page: Scrape. A known list: Batch Scrape. A site section: Crawl. Discover pages first: Search or Map. Return defined fields: Extract/JSON.

Access boundary

Projects and API keys

Each calling service receives its own project and key, keeping limits, errors, operations, and usage attributable to the correct workload.

01Project

Defines workload ownership, limits, and AI policy.

02Gateway

Checks the key, route, and request policy.

03Firecrawl Core

Performs collection, search, or a background job.

04Result

Returns to the caller; large bodies are not stored in operational PostgreSQL.

Keep keys server-side

Do not put administrative or upstream keys in frontend code, browser storage, URLs, or public examples. Applications should use project-scoped gateway keys.

Search and AI

Discover sources, then work with their meaning

Search answers “where is the information?” and can retrieve the content of matching pages. AI functions then map content to a schema or summarize it.

Search

Search results plus optional full content. Use it when the URLs are unknown.

Research

Finds publications through a scholarly index and public GitHub sources. It is a research layer, not an LLM profile.

Agent

Receives a goal and uses web tools within defined limits. It is a separate Firecrawl Cloud capability; Ollama does not replace the Spark models.

Extract / Summary

An LLM maps content to fields or a shorter account. Verify critical facts against sources.

A provider profile and project policy are separate checks

Even a READY provider is unavailable when the current project disallows cloud models or disables AI. The router selects only profiles permitted by that project.

Automation

Background jobs, schedules, and event delivery

Crawl, Batch Scrape, and Extract run asynchronously. Agent joins the same lifecycle only after a cloud provider is connected. Jobs expose lifecycle and errors; monitors and webhooks turn a request into a repeatable workflow.

  • Jobs: status, cancellation, duration, result count, and Core error.
  • Operations: project and key attribution without persisting full result bodies.
  • Monitors: bounded recurring runs.
  • Webhooks: signed delivery, retry policy, and attempt history.

Before the first request

Check permission and load

Technical reachability is not permission for automated collection. Check purpose, site terms, robots policy, personal data, copyright, and the impact of request volume.

1 · URLPublic HTTP(S), no private networks or service addresses.
2 · RightPermission, a contractual basis, or an allowed public source.
3 · RulesSite terms and robots policy allow the selected path.
4 · ScaleDepth, concurrency, and frequency are safe for the source.
5 · DataStore only what is needed and define retention.

robots.txt is an instruction mechanism for automated clients, not an authorization system. Terms and applicable law remain separate constraints.

Runtime

How to read capability status

Dashboard readiness covers the gateway, PostgreSQL, and Core reachability. LLM, browser, and research providers have separate readiness checks.

SignalIt provesIt does not prove
Dashboard readyThe panel, operational PostgreSQL, and Core connection are available.That a specific model, browser, or research provider is ready.
LLM profile READYThe profile passed its check and loaded a model catalog.That the current project permits the profile.
Job COMPLETEDCore finished that background operation.That every page returned useful content; inspect counts and errors.
